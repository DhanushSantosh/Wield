# Release channels and converter packaging research

Researched 2026-10-09 for Wield's Linux Tauri v2 AppImage. This is a decision note, not evidence that any proposed gate or bundle already works.

## Channel contract

- Use immutable SemVer tags: `vX.Y.Z-beta.N` for beta, `vX.Y.Z` for stable. A prerelease sorts before the matching stable version under [SemVer precedence](https://semver.org/#spec-item-11). Validate that the tag's version equals `tauri.conf.json` and any other published version field before building. The current workflow's `v*` trigger accepts malformed tags and does not distinguish channels ([local workflow](../../.github/workflows/release.yml)).
- GitHub Releases are based on tags. Create a **draft** with the binary, checksum, notes, and any other assets attached, verify it, then publish it as `prerelease: true` for beta or `prerelease: false` for stable. GitHub's API does not allow a draft or prerelease to be marked `latest`; explicitly use `make_latest: false` for beta and `true` for stable. This keeps `/releases/latest` on stable ([GitHub release API](https://docs.github.com/en/rest/releases/releases), [release management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)).
- Consider enabling release immutability. GitHub recommends attaching assets while the release is a draft because published immutable releases cannot have their assets replaced, added, or deleted. A failed post-publish step then requires a new version rather than mutating an existing release ([GitHub release immutability](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes), [release management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)).
- Keep `tauri-action` in build-only mode and create/upload through `gh` for this repo: its release API path failed in live Wield tests while its build and the `gh` release path succeeded ([local evidence](../testing.md), [tauri-action build-only usage](https://github.com/tauri-apps/tauri-action)).

## Local gate, CI and artifact checks

1. Put the actual quality checks and AppImage build/smoke checks in one checked-in script or equivalent command set that developers run locally and CI invokes unchanged. Local gate should use a clean checkout of the candidate commit, locked Rust/npm dependencies, formatting/lint/tests, version/tag checks, an AppImage build, extraction/ELF inspection, executable smoke tests, and a SHA-256 manifest. A successful local run must be tied to the exact commit and build environment; source changes invalidate it. CI repeats the gate because local success alone cannot prove the GitHub runner or dependency downloads will behave identically. This is a workflow design recommendation based on the build and distribution constraints below.
2. AppImage compatibility depends on build base. Tauri says to build on the oldest target base with WebKitGTK 4.1; newer glibc can make an AppImage fail on older distributions. Keep the `ubuntu-22.04` target or another explicitly supported old base, and test the resulting image on the oldest supported target plus representative desktops. [Tauri AppImage guide](https://v2.tauri.app/distribute/appimage/), [AppImage best practices](https://docs.appimage.org/reference/best-practices.html).
3. The release CI job should get only its needed permissions: `contents: read` for validation/build and `contents: write` for creating a release. Pin third-party actions to reviewed full commit SHAs. Do not interpolate untrusted event text directly into shell script. [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use), [GITHUB_TOKEN permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).
4. Guard `v*` tags with a repository tag ruleset that restricts creation, updates, and deletion; require a reviewed default-branch candidate and passing checks. A tag-push CI workflow alone cannot enforce that a local command was run: GitHub only sees the ref and commit unless a trusted service records a receipt/status for that exact SHA. A local preflight followed by a protected tag creation command is a practical operator gate; an external trusted status/check is needed for strict technical enforcement. [GitHub tag rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [ruleset creation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).
5. Require exactly one AppImage, check it has the expected version/architecture, verify checksum after transfer/upload, and test the **downloaded release asset**, not just the build directory. GitHub's artifact upload/download actions verify transport digests; release asset checksums and optional artifact attestations give users independently checkable evidence. Attestations identify the build workflow, source commit and artifact digest; they must be verified to add value. [GitHub artifact transport](https://docs.github.com/en/actions/tutorials/store-and-share-data), [artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations), [attestation how-to](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).

## Converter dependencies: recommended resolution

The current AppImage contains the Wield executable, but Wield probes converter commands on `PATH` and invokes them as separate processes. The bundler cannot infer these executables from the app's linked `.so` files ([Wield resolver](../../crates/wield-core/src/command.rs), [current packaging record](../packaging.md)). AppImage's own guidance says to include dependencies that cannot be assumed to exist on supported target systems, including helper executables and their data; linked-library tracing alone cannot identify all runtime resources ([AppImage concepts](https://docs.appimage.org/introduction/concepts.html), [native binary packaging](https://docs.appimage.org/packaging-guide/from-source/native-binaries.html)).

**Recommendation:** make the release promise explicit. For beta, a host-dependent converter tier is reasonable only if release notes, setup documentation, and in-app availability messages accurately say which tools need host packages. For stable, prioritize a self-contained core converter set and do not call the AppImage fully portable until a clean target machine can run every advertised tool. Bundle helpers deliberately, resolve bundled paths before host `PATH` with a documented fallback policy, and run capability and real conversion smoke tests from the extracted AppImage. Tauri supports `bundle.externalBin` with target-triple-suffixed binaries and `bundle.resources` for data files; AppImage's `AppRun` may set paths needed by child processes ([Tauri sidecars](https://v2.tauri.app/develop/sidecar/), [Tauri resources](https://v2.tauri.app/develop/resources/), [AppImage AppRun](https://docs.appimage.org/packaging-guide/manual.html)).

| Dependency | Packaging implication |
| --- | --- |
| Pandoc | Official Linux executable is statically linked and needs no external data files; a good first bundled helper, subject to version/architecture and license review ([Pandoc installation](https://pandoc.org/installing.html)). |
| Tesseract | Bundle engine **and** at least the supported language traineddata, and point the process at the data directory; binary presence alone is insufficient ([Tesseract installation](https://github.com/tesseract-ocr/tessdoc/blob/main/Installation.md)). |
| ImageMagick | Include configuration/delegates and test actual supported formats. Its delegate configuration may call external programs such as Ghostscript; binary presence does not prove a format works. Include its license and attribution when redistributing ([ImageMagick resources](https://imagemagick.org/resources/), [license](https://imagemagick.org/license/)). |
| FFmpeg | Record configure flags and codec coverage, then test every output format Wield offers. Optional components can change the build from LGPL to GPL and impose different redistribution obligations ([FFmpeg legal guidance](https://www.ffmpeg.org/legal.html)). |
| qpdf | Bundle executable with its shared libraries using the selected AppImage packaging process; test merge and split operations on clean target systems ([AppImage native binary guide](https://docs.appimage.org/packaging-guide/from-source/native-binaries.html)). |
| Ghostscript | Review its AGPL or commercial redistribution terms before putting it in the AppImage; this is a release decision, not merely a copy operation ([Ghostscript licensing](https://ghostscript.com/releases/gsdnld.html), [Ghostscript FAQ](https://ghostscript.com/faq/)). |
| LibreOffice | Treat as a separate packaging spike because a single `soffice` executable is not the whole office runtime. If it cannot be made relocatable and tested across supported systems, keep this capability explicitly host-dependent rather than ship a broken partial bundle. AppImage requires runtime resources to be relocatable ([AppImage native binary guide](https://docs.appimage.org/packaging-guide/from-source/native-binaries.html)). |

For every redistributed helper, record upstream version, source URL, hashes, license/notice and source obligations, dynamic libraries, resource files, and a real invocation test. Avoid silent network downloads at app run time; they would make availability dependent on network state and bypass release artifact verification. This final sentence is a Wield release recommendation, not a claim from upstream documentation.
